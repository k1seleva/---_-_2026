# Карта проекта: за что отвечает каждый файл

Как читать: сначала раздел «Типовые файлы модуля» (у всех шести модулей одинаковый набор),
затем раздел конкретного модуля. В конце — «Путь запроса»: какие файлы срабатывают по очереди
в ключевых сценариях.

## Правило, которое держит архитектуру

- Модуль меняет **только свои** таблицы.
- Чужие данные он **читает** через `facade.py` другого модуля.
- Чужие данные он **меняет** только через **событие** (`common/events`). Тот, кто владеет данными, ловит событие в своём `handlers.py`.
- Это правило проверяет `tests/test_architecture.py`.

## `apps/processing/` — модуль обработки результатов

Принимает протокол, достаёт текст, находит находки с цитатой, подсвечивает значимое в каждом фрагменте (без ранжирования) и сообщает «документ обработан».

| Файл | Отвечает за |
|---|---|
| `models.py` | `StudyDocument` (протокол и его версии), `ProcessingJob` (запуск обработки: движок, версия промпта, ошибка), `ExtractionResult` (JSON агента + итог разметки и контроля ИИ, `analysis`: маркеры и триггеры, `advice_meta`), `Finding` (находка + цитата + атрибуты + `rule_id` + `source`: словарь, оба или только ИИ), `RoutingAdvice` (совет ИИ по маршрутизации: текст, обоснование, цитата, уверенность, маршрут и исполнитель, проверка по тексту), `ProtocolSegment` (каждый фрагмент протокола: раздел, подсветки, связь с пунктом заключения, `llm_labels`: что увидел ИИ-агент), `UploadBatch` (пачка), `QualityRun` (проверка качества: сводка и строки по протоколам), `FocusProfile` и `SegmentPin` (приоритеты и закрепления врача), `FindingDefinition`, `SpecialtyAlias`, `AttentionRule` (настройки) |
| `services/text_extraction.py` | Текст из .docx (схлопывает объединённые ячейки выгрузки 1С), .doc (LibreOffice/antiword), .json; разбор шапки: тип исследования, дата, врач |
| `services/schemas.py` | **Формат JSON агента** (pydantic): находки, рекомендации, выжимка. Это вход модуля маршрутизации |
| `services/ai_agent.py` | **Интеграция с LangChain**: абстракция `FindingExtractor`, агент на правилах, LangChain-агент со structured output, гибрид с источником каждой находки (`source`, `engines`), фабрика модели по провайдеру (`num_ctx`, тайм-аут Ollama), `describe_llm_error`; поиск раздела «Заключение», отрицания |
| `services/segmentation.py` | Режет протокол на фрагменты (предложения и строки «Параметр: значение») с точными границами; склеивает предложения, разорванные переносом строки; определяет раздел и орган. `verify_coverage` доказывает, что ни один символ не потерян |
| `services/annotation.py` | **Подсветка значимого без ранжирования**: тип фрагмента, причины подсветки (`HIGHLIGHT_TYPES`: находка, шкала, порог, размер, сторона, «не вынесено в заключение», сомнение…), лексикон признаков, отрицания, связь детали описания с пунктом заключения (в пределах органа), пороги внимания; LLM-разметчик может только добавить подсветку с дословной цитатой |
| `services/normalization.py` | Нормализация текста для поиска (ё/е, латиница в кириллице, Т вместо T в TI-RADS, пробелы) с картой смещений: найденное возвращается в позициях исходного текста, отмечается `corrected` |
| `services/scoring.py` | Уверенность маркера и триггера: база по виду правила + факторы с причинами (отрицание, сомнение, исправленный текст, есть в заключении); уровни high, medium, low |
| `services/markers.py` | **Маркеры и триггеры**: `MarkerExtractor` (находка, шкала, признак, размер, количество, процент, сторона, сомнение, отрицание; у каждого id, позиция, цитата, уверенность, `rule_id`), `resolve_overlaps` (слияние, вложенность, слои, список наложений), `TriggerDetector` (маршрут, экстренное, проверка; дедупликация), `analyze_protocol`, палитра с контрастом WCAG AA; источник маркера и триггера (`SOURCE_TITLES`, `confirm_by_llm`, `share_known_codes`) |
| `services/routing_advice.py` | **Советы ИИ по маршрутизации**: `RoutingAdvisor`, `QwenRoutingAdvisor` (LangChain, structured output), `DemoRoutingAdvisor` (из триггеров, с пометкой), `ground_advice` (цитата, маршрут, специальность), `RoutingAdviceService` (ответ модели целиком и время в `advice_meta`; при сбое модели ошибка без подмены демо), `configured_engine` |
| `services/grounding.py` | **Контроль ИИ**: цитата дословно есть в тексте, число есть в тексте, код из словаря, фрагмент существует; что ИИ пропустил, остаётся по правилам; попытки снять подсветку правил учитываются (`hidden_ignored`). Отчёт `GroundingReport` |
| `services/presenter.py` | `layered_evidence_html` и `evidence_css`: подсветка маркеров слоями без потери текста, метки триггеров, режимы показа. Экран врача: экстренное предупреждение, «В фокусе» (закрепления, личные приоритеты, фильтры), заключение с деталями, изменения описания по органам, рекомендации, неклассифицированное, норма, служебное. Порядок — как в протоколе. Инвариант: каждый фрагмент показан ровно один раз |
| `services/quality.py` | **Проверка качества аналитики**: `ProtocolEvaluator` (один протокол «всухую» + инварианты), `summarize` (сводка; с разметкой — точность, полнота, F1, расхождения), `parse_labels`, `rows_to_csv`, `QualityRunService` (до `QUALITY_MAX_PROTOCOLS` за прогон, файлы удаляются после) |
| `services/inbox.py` | Серверная папка-наблюдатель: забирает файлы по клиникам, раскладывает в processed / failed |
| `services/dictionary.py` | Снимок словарей из БД для агентов (агенты не ходят в базу сами) |
| `services/pipeline.py` | Сценарии: приём файла (проверка, дедупликация, версии, очередь), обработка (текст → агент → сохранить → событие, время шагов), аннулирование |
| `services/jobs.py` | Очередь разбора пачки: постановка (поток сайта / Celery / sync), атомарный захват задачи, возврат зависших, повтор с ИИ, ход пачки и оценка остатка |
| `tasks.py` | Celery-задачи `process_document`, `watch_inbox`, `run_quality_check`, `generate_routing_advice` |
| `api/batches.py` | API пачек: `POST /api/v1/processing/batches/` (файлы или zip), список и детали |
| `api/quality.py` | API проверки качества: `POST /api/v1/processing/quality-runs/` (до 100 протоколов + labels.csv), `GET …/{id}/` — сводка и строки |
| `facade.py` | Документ, находки, полный текст, разметка с экраном врача и отчётом контроля ИИ (`get_annotation`), аналитика признаков (`annotation_stats`), разбор текста рекомендаций; разметка маркеров (`get_analysis`, `evidence_view`), советы ИИ (`routing_advice`), сводка триггеров (`trigger_stats`), последний прогон качества |
| `handlers.py` | Пустой: модуль только публикует события |
| `management/commands/check_llm.py` | Проверка Qwen на своём компьютере: синтетический протокол через все шаги (находки, разметка, триггеры по источникам, советы с ответом модели); ничего не сохраняет |
| `management/commands/process_queue.py` | Очередь разбора отдельным процессом без Celery (`--once` — разобрать очередь и выйти) |
| `management/commands/regenerate_advice.py` | Советы заново после подключения Qwen: где демо или ошибка (`--all` — все, `--document` — один) |
| `management/commands/evaluate_protocols.py` | То же, что «Качество разбора», для папки на диске без лимита: отчёт CSV, сводка, точность и полнота по разметке (использует `services/quality.py`); `--summary-json` сохраняет только счётчики для публикации |
| `views.py` | Загрузка пачкой (файлы, папка, zip, слежение за папкой), закрепление фрагментов врачом, страницы «Качество разбора» (запуск, отчёт с фильтрами, CSV) |

## `apps/routing/` — модуль составления маршрута (ядро цикла)

Превращает находки в маршрут и двигает его по этапам до закрытия.

| Файл | Отвечает за |
|---|---|
| `models.py` | Настройки: `TriggerRule` (строка матрицы), `RouteTemplate` + `RouteTemplateStep`, `EscalationPolicy`. Состояние: `PatientRoute` (маршрут, витки через `parent`), `RouteStep` (этап, таймер, попытка записи), `RouteEvent` (журнал «кто, что, когда, на каком основании») |
| `services/matrix.py` | Матрица: находка + условия (например, BI-RADS ≥ 3) → правило; один маршрут на клиническую группу; объяснение «почему не сработало» |
| `services/builder.py` | Создание маршрута из JSON агента (этапы шаблона + таймеры из рекомендаций); маршрут из принятой координатором правки (`build_manual`); пересчёт при исправлении и закрытие при аннулировании протокола |
| `services/planner.py` | **Двигатель цикла**: активировать следующий этап, запись, отмена, неявка, тактика врача → новые этапы, события стационара, выписка → новый виток, действия пациента, правки координатора |
| `services/state_machine.py` | Допустимые переходы статусов маршрута; каждый переход пишется в журнал и публикуется событием |
| `services/escalation.py` | «Пульс»: включает этапы, у которых подошёл срок, и проходит лестницы напоминаний (24 ч → 72 ч → звонок → 14 дн. → 30 дн. «не вовлечён») |
| `services/journal.py` | Одна функция записи в журнал маршрута |
| `tasks.py` | Celery-задача тика эскалаций |
| `handlers.py` | Реакция на: документ обработан/исправлен/аннулирован, запись, отмену, неявку, итог приёма, доставку уведомления, действие пациента, правку координатора, события МИС |
| `facade.py` | Маршрут, этап, незавершённые маршруты (для баннера врачу), маршруты по протоколу, проверка «запись строго по маршруту», объяснения матрицы, предпросмотр маршрутов без записи, подробности сработавших правил матрицы (`match_rules_detail`), каталог маршрутов для корректировки совета (`route_catalog`) |
| `api/views.py` | Маршруты пациента, журнал, `generate` (маршрут из JSON, режим `dry_run`), CRUD матрицы |

## `apps/audit/` — модуль проверки рекомендаций (необходимость коррекции маршрута)

Сверяет, что рекомендовал врач, с показаниями по находкам и с текущим маршрутом. Пропуск выносит на обсуждение координатору; сам маршрут не меняет.

| Файл | Отвечает за |
|---|---|
| `models.py` | `IndicationRule` (матрица показаний: находка + условия → консультация специалиста или обследование, срок, тяжесть пропуска), `RecommendationAudit` (проверка протокола или приёма: вердикт, итог), `AuditIssue` (замечание с цитатой-основанием, предложенная правка, решение координатора) |
| `services/indications.py` | Показания из находок и значимых фрагментов разметки (в том числе «только в описании», «с сомнением») |
| `services/recommendations.py` | Рекомендации протокола и назначения приёма → единый список пунктов; «лечащий врач» без профиля — расплывчатый пункт |
| `services/auditor.py` | **Логика проверки**: показание закрыто рекомендацией, приёмом или этапом маршрута; срок не позже допустимого; вердикт «достаточно / есть замечания / недостаточно» |
| `services/service.py` | Сценарии: проверить протокол и приём, сохранить, сообщить координатору, применить решения, снять проверки с аннулированного протокола |
| `handlers.py` | Документ обработан/исправлен/аннулирован, приём завершён, решение координатора |
| `facade.py` | Проверки по протоколу, список, статистика (вердикты, частые пропуски, точность правил по решениям координатора), проверка без сохранения |
| `api/views.py` | `check/` (без сохранения, можно передать свои рекомендации), `audits/`, `stats/`, `documents/{id}/` |

## Путь запроса: какие файлы срабатывают

**1. Загрузили протокол**
`processing/api/views.py` → `processing/services/pipeline.py` (ingest) → `processing/tasks.py` → `pipeline.py` (run) → `text_extraction.py` → `ai_agent.py` → событие `document_processed` → `routing/handlers.py` → `routing/services/builder.py` + `matrix.py` → `planner.py` активирует этап → событие `step_activated` → `patients/handlers.py` → `patients/services/notifications.py`.

**2. Пациент записался**
`patients/views.py` или `api/views.py` → `patients/services/booking.py` → проверка через `routing/facade.py` → запись через `doctors/facade.py` → `doctors/services/booking.py` → событие `appointment_booked` → `routing/handlers.py` (этап «записан») и `patients/handlers.py` (подтверждение).

**3. Врач завершил приём**
`doctors/views.py` → `doctors/services/booking.py` (`VisitService`, тактика обязательна) → событие `visit_completed` → `routing/services/planner.py` (новые этапы) и `coordinator/handlers.py` (воронка; спор, если врач не согласен).

**4. Прошло время**
Celery beat → `routing/tasks.py` → `routing/services/escalation.py` → событие `step_escalated` → `patients/handlers.py` (напоминание) или `coordinator/handlers.py` (задача на звонок).

**5. Проверка рекомендаций и решение координатора**
`processing/services/pipeline.py` (разметка в событии `document_processed`) → `routing/handlers.py` строит маршрут → `audit/handlers.py` → `audit/services/service.py` + `auditor.py` → событие `audit.completed` → `coordinator/handlers.py` → `coordinator/services/audit_reviews.py` (обсуждение + задача). Решение координатора → `correction_approved` → `routing/handlers.py` (правка или новый маршрут) и `audit_resolved` → `audit/handlers.py` (точность правил).

**6. Событие из МИС 1С** (госпитализация, операция, выписка)
`gateway/views.py` → `gateway/mis.py` → событие `mis.*` → `routing/services/planner.py` (`on_mis_event`); выписка → новый виток → `doctors/handlers.py` записывает на контроль заранее.

**7. Маркеры, триггеры и совет ИИ**
`processing/services/pipeline.py` (run) → `normalization.py` + `annotation.py` → `markers.py` (`MarkerExtractor` → `resolve_overlaps` → `TriggerDetector`, правила матрицы через `routing/facade.py`) → `ExtractionResult.analysis` → после фиксации транзакции `tasks.generate_routing_advice` → `routing_advice.py` (Qwen или демо, `ground_advice`) → `RoutingAdvice`. Координатор оценивает совет на карточке случая → `coordinator/services/advice.py` → `AdviceReview`; маршрут по совету сам не меняется.

**8. Пациент входит в кабинет**
Вход сотрудника: `gateway/staff_views.py` → `gateway/staff_auth.py` (пароль, роль, для врача его карточка) → сессия `staff_role` (+ `doctor_id`) → `StaffAccessMiddleware` пускает в `/coordinator/` и `/processing/` только координатора, в `/doctor/` только врача, `doctors/views.py` показывает врачу только его приёмы.

`patients/views.py` (`login_view`) → `patients/services/auth.py` (проверка пароля, блокировка) → сессия `patient_id` → `patient_required` на страницах кабинета и `PatientAccess` в API → `services/push.py` показывает, как выглядит push.
